# 선택 주제의 요구사항 — 3조

- 학교가 확정한 20개 주제 중 선택한 주제: 16번 광주·전남 1일 또는 1박 2일 관광코스 추천
- 해결할 문제와 대상 사용자:
  - 문제: 반값여행 같은 관광소비 환급제 정보가 시군별 공고로 흩어져 있고 기간·대상·한도·절차가 제각각이다. 사전 신청·증빙·정산 중 하나만 놓쳐도 환급을 받지 못한다. 기존 코스 추천은 '어디 가면 돌려받는가'를 알려 주지 않는다.
  - 1차 사용자: 광주 거주 20~40대. 자차로 전남 당일·1박2일 여행을 떠나는 커플·친구·가족.
  - 2차 사용자: KTX로 광주송정역에 도착해 1박2일을 보내는 외지 관광객.
- 행사 안에 완성할 핵심 기능(최대 3개):
  1. F1 환급 우선 관광지 추천: 여행 조건을 받아 환급제 운영 지역을 먼저, 그다음 취향·이동시간 순으로 지역 3곳과 관광지 후보를 추천한다.
  2. F2 이동순서 일정표·추천 이유: 시간·거리·환급제 조건 안에서 방문 순서와 시간표를 만들고 장소별 추천 이유를 붙인다.
  3. F3 환급 혜택 안내: 자격 확인, 예상 환급액, 여행 전·중·후 할 일과 실제 날짜 기한, 공식 신청 링크를 보여 준다.
- 입력 데이터와 확보 방법(주최 측 제공 데이터 가정 금지):
  - 공공데이터포털 API 4종(팀이 인증키 발급 완료): 전국관광지정보표준데이터, 한국관광공사 국문 관광정보(KorService2), 관광지별 연관 관광지(TarRlteTarService1), 기초지자체 중심 관광지(LocgoHubTarService1). 행사 전에 광주 5개 구·전남 22개 시군 범위로 수집 스크립트를 1회 돌려 SQLite에 캐시한다.
  - 환급제 DB: 공개 API가 없어 팀이 지자체·문체부 공고와 보도를 확인해 JSON 시드로 직접 입력한다(2026-10-30 기준 4종).
  - 사용자 입력: 일정 유형, 여행 시작일, 출발지, 관심 분야, 거주 시군구, 인원, 이동수단.
  - 대체 경로: API가 실패하거나 시군 캐시가 5곳 미만이면 팀이 고른 시연 데이터(시군별 15~20곳)로 채운다.
- 결과 화면과 정상 동작을 확인할 기준:
  - 조건 입력 → 추천 지역 카드 3장(환급 배지 포함) → 시간대별 일정표 → 환급 카드·예상 환급액·할 일 타임라인이 한 흐름으로 이어진다.
  - 아래 '수용 기준'을 pytest와 시연 시나리오로 확인한다.
- 이번에 구현하지 않을 범위:
  - 숙박·교통 실제 예약과 결제, 전국 단위 최적화
  - 환급 사전 신청·정산 대행(공식 페이지로 연결만 한다)
  - 회원가입·로그인, 거주 시군구 외 개인정보 저장
  - 예산 잔액 실시간 연동(접수 상태는 수동 갱신)
  - 영수증 인식, 환급 규정 Q&A 챗봇(RAG), 지도 동선(S3)·코스 공유(S4)·캘린더 추가(S5)는 시간이 남을 때만

기록 저장 판단: 필요하다. 단, 사용자 기록이 아니라 관광 캐시(place, hub_rank, related_place), 환급제(refund_program), 생성 코스(course)만 저장한다. 공통 Record CRUD 예제는 쓰지 않고 테이블은 backend/app/team/models.py에 추가한다. 거주 시군구·인원은 판정에만 쓰고 저장하지 않는다.

외부 데이터를 못 구한 경우: 시연 데이터와 환급제 시드만으로 F1→F2→F3 흐름을 재현할 수 있게 한다. 시연 시점에 접수 중인 환급제가 없으면 '기준일'을 운영기간 안 날짜로 두고 화면에 기준일을 표시한다.

## 용어

- 환급제: 여행 지출의 일부를 지역화폐 등으로 돌려주는 지자체 사업(반값여행, 지역사랑 휴가지원 등).
- 적용 가능: 여행 기간이 운영기간 안이고, 접수 상태가 '접수중'이며, 사전 신청 기한 전이고, 거주지·인원 조건을 충족한 상태.
- 1순위 그룹: 적용 가능한 환급제가 있는 시군. 2순위 그룹: 나머지 시군.
- 정보 기준일(verified_at): 팀이 공고를 마지막으로 확인한 날짜.

## 요구사항 1. 환급 우선 관광지 추천 (F1)

**사용자 이야기:** 여행자로서, 내가 가는 날 환급받을 수 있는 지역을 먼저 보고 싶다. 그래야 같은 여행을 더 싸게 다녀올 수 있다.

### 처리 규칙

- 입력: 일정 유형(당일/1박2일), 여행 시작일, 출발지(광주 5개 구, 광주송정역, 목포역, 순천역, 여수엑스포역), 관심 분야 1~3개(자연·바다, 역사·문화, 맛집, 체험·레저, 힐링·산책), 거주 시군구, 인원(1명/2명 이상), 이동수단(선택, 기본 자차).
- 이동시간 상한: 출발지에서 편도 추정 시간이 당일 150분, 1박2일 240분을 넘는 시군은 뺀다.
- 그룹 안 점수(100점): 취향 적합도 40, 이동 접근성 30(편도 60분 이하 만점, 상한까지 선형 감소), 대표 관광지 20(중심 관광지 상위 5곳 중 관심 분야 일치 1곳당 4점), 시기 가산 10(여행일 축제·행사 1건 이상). 동점이면 환급 한도가 큰 시군이 앞이다.
- 관심 분야는 KorService2 분류체계(lclsSystm) 대분류에 매핑한다. 코드값은 분류체계 코드조회로 받아 매핑 표를 만든다.
- 광주 연결: 출발지가 광주이고 당일 편도 90분 이하(1박2일은 항상)면 광주 문화관광지 1곳을 첫 장소 후보로 함께 고른다.
- 관광지 후보: 선택 시군의 중심 관광지 상위 10곳 + 그 연관 관광지 상위 10곳(같은 시군 우선)을 관심 분야로 거른다.

### 수용 기준

1. WHEN 사용자가 여행일과 거주 시군구를 입력하면, THE SYSTEM SHALL 적용 가능한 환급제가 있는 시군을 결과 목록 맨 앞에 표시한다.
2. WHEN 2순위 시군의 점수가 1순위 시군보다 높더라도, THE SYSTEM SHALL 그 시군을 1순위 시군 뒤에 표시한다.
3. IF 거주 시군구가 프로그램의 제외 지역이면, THEN THE SYSTEM SHALL 그 프로그램을 적용 가능으로 판정하지 않는다.
4. IF 여행일 기준 사전 신청 기한이 지났으면, THEN THE SYSTEM SHALL 배지를 '신청 마감'으로 표시하고 그 시군을 1순위에서 뺀다.
5. THE SYSTEM SHALL 추천 지역마다 추천 이유 태그를 2개 이상 표시한다.
6. IF 적용 가능한 환급제가 하나도 없으면, THEN THE SYSTEM SHALL 2순위 그룹만 추천하고 "선택한 날짜에 신청 가능한 환급제가 없어요"와 가장 가까운 접수중·운영 예정 프로그램을 함께 표시한다.
7. IF 시군 캐시에 관광지가 5곳 미만이면, THEN THE SYSTEM SHALL 시연 데이터로 후보를 채운다.

## 요구사항 2. 이동순서 일정표·추천 이유 (F2)

**사용자 이야기:** 여행자로서, 고른 지역을 시간 순서대로 어떻게 돌지 바로 알고 싶다. 그래야 따로 동선을 짜지 않아도 된다.

### 처리 규칙

- 기본 장소 수: 당일 4~5곳, 1박2일 식사·숙박 포함 8~10곳.
- 시간표 틀: 당일 관광지① 10:00 → 점심 12:00 → 관광지② 13:30 → 관광지③ 15:30 → 저녁(선택) 17:30. 1박2일 1일차는 광주 문화관광지 10:00에서 시작해 숙박(환급 지역)으로 끝나고, 2일차는 숙소 출발 09:30, 귀가 16:00이 기준이다.
- 체류시간 기본값: 관광지 90분, 문화시설 60분, 레포츠·체험 120분, 식사 60분. 소개정보에 관람 소요시간이 있으면 그 값을 쓴다.
- 이동시간 추정: 직선거리 20km 이상은 거리×1.3÷60km/h, 20km 미만은 거리×1.4÷35km/h, 장소마다 +5분. 대중교통은 ×1.5 후 '실제 배차 확인' 문구를 붙인다.
- 순서 정렬: 출발지(2일차는 숙소)에서 최근접 이웃으로 잇고 2-opt로 한 번 정리한다. 식사는 기준 시각에 가장 가까운 자리에 끼운다.
- 식당: 직전 장소 반경 5km 음식점(contentTypeId=39) 중 연관 관광지에 함께 등장한 곳을 먼저 고른다. 환급제가 지역 가맹점만 인정하면 환급 지역 안 업소만 고른다.
- 추천 이유: 근거 태그를 규칙으로 먼저 만들고, Bedrock(기본 Claude Haiku 4.5)은 태그와 overview 앞 200자를 받아 장소당 30자 이내 한 문장으로 다듬는다. POST /api/ai/generate를 하루 일정당 1회, 코스당 최대 2회만 부르고, 식당·숙소는 규칙 문장만 쓴다. 금액·기한·운영시간은 AI 문장에 넣지 않고 DB 값을 화면에 직접 표시한다.
- 출력 JSON은 trip_type, region, days[].items[](order, start, end, kind=spot·meal·stay, place, move_min_from_prev, reason_tags, reason_text, refund_note), estimated_spend_krw, estimated_refund_krw를 가진다.

### 수용 기준

1. WHILE 일정 유형이 당일이면, THE SYSTEM SHALL 마지막 장소 종료 시각을 19:00 이전으로 맞춘다. 1박2일 2일차는 귀가 출발을 17:00 이전으로 맞춘다.
2. IF 연속한 두 장소의 추정 이동시간이 40분을 넘으면, THEN THE SYSTEM SHALL 그 구간에 경고를 표시한다.
3. IF 여행일이 장소의 휴무일이거나 운영시간 밖이면, THEN THE SYSTEM SHALL 그 장소를 일정에 넣지 않고 다음 후보로 바꾼다. 휴무 정보를 읽지 못하면 '방문 전 확인' 배지를 단다.
4. IF AI 호출이 429·502로 실패하면, THEN THE SYSTEM SHALL 모든 장소에 근거 태그 1개 이상과 규칙 문장을 표시한다.
5. WHEN 환급 지역 1박2일 코스를 만들면, THE SYSTEM SHALL 숙소를 그 지역 안에서 고른다.
6. IF 환급제에 필수 방문지가 있으면, THEN THE SYSTEM SHALL 그 장소를 일정에 고정해 포함한다.
7. IF 환급제에 숙박 요일 조건이 있으면, THEN THE SYSTEM SHALL 조건에 맞는 날에만 숙박을 넣고, 맞지 않는 날짜면 날짜 변경을 먼저 제안한다.
8. WHEN 같은 코스를 다시 요청하면, THE SYSTEM SHALL 저장해 둔 추천 문장을 재사용하고 AI를 다시 부르지 않는다.

## 요구사항 3. 환급 혜택 안내 (F3)

**사용자 이야기:** 여행자로서, 이 여행으로 얼마를 돌려받는지와 언제 무엇을 해야 하는지 알고 싶다. 그래야 절차를 놓치지 않는다.

### 처리 규칙

- 자격 확인: 거주지 제외 지역, 나이·청년 조건, 운영기간·접수 상태, 사전 신청 기한, 숙박·방문 조건, 인정 결제 수단을 '가능 / 확인 필요 / 불가'로 판정한다.
- 예상 환급액 = min(인정 지출 × 환급률, 한도). 환급률·한도는 인원·청년 여부·박 수에 맞는 값을 쓴다. 최소 지출 조건이 있으면 먼저 확인하고, 모자라면 '○원 더 쓰면 환급 대상'으로 안내한다.
- 인정 지출 = 식사 횟수 × 인원 × 1인 식비(기본 12,000원, 사용자 수정) + 숙박 1박 요금(객실 요금, 없으면 기본 100,000원) + 이용요금을 읽은 유료 관광지·체험 요금. 인정 업종·지역이 정해진 프로그램은 그 항목만 더한다.
- 예: 2인 1박2일, 식사 4끼×2명×12,000원 + 숙박 100,000원 = 196,000원 → 환급 98,000원.
- 단계별 절차: 여행 전 사전 신청(기한 = 시작일 − N일) → 여행 전 결제 준비 → 여행 중 소비·증빙 → 여행 후 정산 신청(기한 = 종료일 + N일) → 환급·사용 안내.

### 수용 기준

1. WHEN 사용자가 환급 지역 코스를 열면, THE SYSTEM SHALL 환급 카드(제도명, 환급률, 한도, 운영기간, 접수 상태, 정보 기준일, 공고 링크)·예상 환급액·단계별 절차를 한 화면에 표시한다.
2. THE SYSTEM SHALL 예상 환급액이 한도를 넘지 않게 계산하고, 계산에 쓴 지출 항목을 펼쳐 보여 준다.
3. THE SYSTEM SHALL 각 단계 기한을 여행일 기준 실제 날짜로 계산해 표시한다.
4. IF 정보 기준일이 7일을 넘었으면, THEN THE SYSTEM SHALL '공고 재확인 필요' 경고를 표시한다.
5. THE SYSTEM SHALL 신청 버튼을 환급제 DB에 저장된 공식 URL로만 연결한다.
6. THE SYSTEM SHALL 예상 환급액 옆에 '예상치이며 실제 환급은 지자체 심사 결과를 따른다'는 문구를 표시한다.

## 요구사항 4. 데이터 수집·환급제 등록 (S1·S2, 필수 보조)

### 수용 기준

1. THE SYSTEM SHALL 공공 API 4종을 수집 스크립트로 미리 받아 SQLite에 저장하고, 화면 요청에는 캐시만 읽는다. 상세 정보는 후보 장소만 받아 캐시한다.
2. THE SYSTEM SHALL 모든 관광공사 API에 serviceKey, MobileOS=WEB, MobileApp=서비스명, _type=json을 보낸다. 삭제 예정인 지역코드조회·서비스분류코드조회는 쓰지 않는다.
3. THE SYSTEM SHALL 내부 지역 키를 시군구 코드 하나로 맞추고, KorService2의 lDongRegnCd·lDongSignguCd와 연관·중심 관광지의 areaCd·signguCd를 매핑 표로 대조한다.

5. THE SYSTEM SHALL 연관·중심 관광지를 이름 정규화 + KorService2 키워드 검색 + 같은 시군구 조건으로 contentid에 맞추고, 실패분은 수동 매핑 표로 채운다.
6. THE SYSTEM SHALL 환급제를 JSON 시드로 등록하고, 각 프로그램에 status와 verified_at을 필수로 둔다.

## 비기능 요구사항

- 기술 스택: .kiro/steering/tech.md를 따른다. 팀 테이블은 backend/app/team/models.py, API는 backend/app/team/routes.py에 둔다. Docker·RDS·Redis·벡터DB는 추가하지 않는다.
- 외부 호출: 공공 API는 lock 파일에 있는 httpx로 부른다. 새 패키지나 AWS 서비스(예: Amazon Location Service)는 멘토 검토를 받는다.
- AI 호출: 공통 POST /api/ai/generate만 쓴다. 분당 20회·하루 600회, 응답 256토큰, 지시문 300자·입력 4,000자 제한을 지킨다. 로컬은 mock 모드로 연동만 확인한다.
- 인증키: 공공데이터 인증키는 서버 .env에만 두고 Git·프론트엔드에 넣지 않는다. httpx params에는 Decoding 키를 넣는다.
- 응답 시간: 지역 추천·일정표는 캐시 기준 3초 안에 보이고, AI 문장은 일정표를 먼저 보여 준 뒤 채운다.
- 장애 대응: 공공 API·Bedrock이 실패해도 캐시와 규칙 문장으로 응답해 화면이 비지 않는다.
- 저작권: 관광공사 이미지는 저작권 유형(cpyrhtDivCd)을 확인하고 출처 '한국관광공사'를 표기한다.
- 개인정보: 로그인이 없다. 거주 시군구·인원은 판정에만 쓰고 저장하지 않는다.
